Linux 首版流程
A / 建立连接
01 · 配置填写 URL + 设备凭据

检测 HTTPS 地址格式、系统证书和鉴权。测试连接调用能力接口，不录音。

02 · 用户按 F9（默认）重新查询 capabilities

按客户端快捷键时记录输入目标；读取协议、模型、名额和音频 / 流控限制。查询不预留名额。

03 · can_start=true连接 WSS，发送 start

携带服务实例与模型代次；连接后 5 秒内发送。状态变化由服务端拒绝。

04 · 收到 ready绑定会话，打开麦克风

核对身份与发送额度；再次检查 F9 开始时的目标，变化则只复制。握手失败不开始收音。

若模型未加载、不支持当前模式或名额已满，显示具体原因；Linux 客户端不会替服务器加载或切换模型。

B / 持续听写 · 三条任务同时运行

① 收音任务

麦克风 → 20 ms VAD 帧
→ 80–160 ms PCM 包 → 有界队列

默认静音约 1 秒时加入 flush 标记；麦克风继续录音。设备断开时停止本轮并保留固定文字。

② 发送任务

等待 flow 额度 → 顺序发音频
→ 顺序发 flush / finish

sent + 本帧样本数 ≤ audio_send_limit。未发送音频最多 2 秒；超限明确停止并取消，不静默丢音频。

③ 接收与交付任务

校验身份 + seq + text 前缀
→ 候选显示 / 固定文字增量粘贴

flow 更新发送额度；pending 只预览。文字交付另排队，慢粘贴不阻塞接收。

每 10 秒发一次 keepalive；默认 30 秒无有效输入会被结束。采集上限与发送额度读取服务能力，当前会话上限为 1 小时。

C / 收尾与异常

再按 F9（默认）：正常结束

停止收音 → 发完已采集音频 → finish → 等 final → 交付最后增量 → 回到可开始状态。

点取消：立即停本轮

先关闭本地自动输入通道，再发 cancel；忽略迟到文字，保留已经收到的固定文字。其他客户端继续运行。

断线 / 模型变化 / 凭据失效

停止收音和自动输入，保留已确认文字并显示原因。重新查询状态后，由用户开始新会话；不回放旧音频。

未配置→检查连接→可开始→连接会话→录音中→收尾中→可开始 / 异常提示
事件去重与文字交付：两份位置分别保存

内存中分别保存“已收到的固定全文”和“交付游标”。当前实现按粘贴键命令成功推进游标，尚未取得目标读取或插入回执。新事件必须匹配实例、模型代次和会话；忽略旧序号，检查固定前缀后仅追加新后缀。

X11 窗口或可观测焦点变化后改为复制；同窗口内标签页、输入框或光标变化未必可检测，需单独验收。断线、取消、App 重启后不自动补贴。外部输入框不提供可靠确认，首版不承诺任意故障下严格 exactly-once；交付失败时保留全文供手动复制。

服务器 → 客户端

按身份与序号处理，文字和音频包无需一一对应

事件关键字段客户端处理
readysession_id、seq、audio_received_samples、audio_processed_samples、audio_send_limit绑定会话，设置初始额度，开始收音。查询成功不能替代这个确认。
flow累计接收 / 已处理样本、audio_send_limit更新允许发送的累计上限，唤醒发送任务。旧事件不重复增加额度。
partialtext 累计固定全文、pending 候选、audio_processed_samples检查固定全文以前次全文为前缀；只输入新后缀。候选只显示。
finaltext、pending、reason、complete正常完成时交付尾字。reason=cancelled 时 complete=false；取消后不再采纳文字。
errorcode、message、retryable、retry_after_ms、固定 text停止本轮，保留本地已确认文字，显示具体原因。后续诊断重试不等于自动恢复录音。
keepalive会话身份、seq、当前音频进度确认连接仍活跃；不当作文字更新。

ready 后，事件都带 server_instance_id + model_generation + session_id + seq。seq 递增但可跳号；它是事件序号，不是字数。建会话前失败可返回 session_id:null, seq:0。

流控按 capabilities 的 flow.window_samples 和实际 ready / flow 的 audio_send_limit 动态读取。R2T2 默认 32000 样本；Qwen 为 max(configured_window, 32000 + max_frame_bytes / 2)，默认 34560，确保整帧能跨过 2 秒推理门槛。audio_processed_samples 只计真实已处理 PCM，包含数字静音，不含未推理缓冲或 80 ms 补零，flush 不清零。

接口边界与设备凭据的取得

实现方式与发布边界

已审核开发范围；性能、安装体积与兼容性待实际验证

新增技术调整 两台目标机已发现的 GTK 版本分别为本机 3.24.41、e15l 3.24.20，均无 GTK4；采用 Rust + GTK3 兼容现有桌面环境，不升级系统 GTK。e15l 为 Ubuntu 20.04，发布构建需兼容其 GTK 与 glibc 基线，不能直接假设 Ubuntu 24.04 构建的二进制可运行。

部分拟采用方式目的
主程序Rust + GTK3；独立客户端工程，首版提供 .deb（包含系统依赖声明），按 Ubuntu 20.04 兼容基线构建适配本机 Ubuntu 24.04 和 e15l Ubuntu 20.04 的现有 GTK3；安装后分别验证。采用 Rust 不代表 GPU 推理会自动变快。
网络与会话异步 HTTP / WS；与 GUI 线程分离；系统证书校验复用现有 V1 语义，发送、接收、保活、交付互不阻塞；不增加本地 HTTP 服务。
音频与 VAD首版复用已验证的 parec 采集方式与 WebRTC VAD 规则；按格式输出 PCM复用系统 PipeWire / PulseAudio 兼容层；不在客户端提取模型特征。
桌面输入X11 使用 xclip / xdotool；GNOME 自定义快捷键调用 App --toggle，经单实例本地 IPC 分发核对目标窗口、顺序追加、不发送回车；可复用行为规范与测试样本。

公网接入规划：本轮不部署

仅规划 · 尚未实现 后续客户端可扩展为通用 HTTPS 根地址；首版仅接受 Tailnet 地址，现有服务启动配置使用 .ts.net 证书名。未来可另设公网 HTTPS 反向代理，仅允许两条移动 V1 路径，并通过可达的 Tailnet TLS 入口访问当前后端。

规划中的网关需要有效证书、WS Upgrade / 长连接支持、保留设备 Authorization、合适的连接限制；额外网关认证不能覆盖设备 Bearer。上游证书和主机名同样校验。

若未来反代改接服务器 loopback，必须严格限制两条 V1 路由，不得整站映射本机管理接口。直接绑定公网地址则需要另改监听配置，并先获得用户针对服务端变更的确认。这些部署均尚未执行。

双机安装与开发后的验收顺序
  • 先测协议：能力检查、握手、额度、序号、固定前缀、finish / cancel / 断线；模拟结果与真实服务器测试分别记录。
  • 分别在本机 Ubuntu 24.04 / GTK 3.24.41 与 ssh sky@e15l 的 Ubuntu 20.04 / GTK 3.24.20 安装；检查包依赖、程序启动、Secret Service、桌面会话及实际麦克风。安装成功不等于识别与输入验收完成。
  • 再测真实 Linux：麦克风、停顿补字、默认 F9 及自定义快捷键、候选字幕、复制及 X11 目标变化；服务器本机 F8 保留并单独检查。
  • 最后测真实双路：服务器本机 PC + 一台 Linux 远端持续至少 10 分钟，确认两端持续出字、无串流、无不断增长的积压；Linux 取消不影响 PC。两台 Linux 分别验证。
  • Linux 与安卓互换占用远端名额；第二个远端应明确收到容量不足。公网验收属于后续规划，本轮不执行。
