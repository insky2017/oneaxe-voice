# R2T2 两路长测：CPU 被动等待

日期：2026-10-03。测试源码为 `48c8f36`，分支为 `codex/multi-stream-capacity`。承接[两路 120 秒对照](preprocessing-e2e-2026-10-02.md)。本轮只测试 R2T2，正式服务尚未启用此优化，容量仍为两路。

## 要点

- 优化配置完成两路各 10 分钟识别。全部音频已处理，最后文字已收齐，后段积压没有增加。
- 优化只设置 `OMP_WAIT_POLICY=PASSIVE`，让 CPU 线程在等待时休息。CPU 仍做音频特征处理，GPU 仍做模型推理。
- 优化配置的服务 CPU 平均占用约 1.05 个逻辑核。这个数包括 API、worker 和推理引擎的 CPU 消耗，不等于整台电脑占用 100%。
- 原配置在约 3 分 22 秒时出现音频积压，测试自动停止。本轮没有完整的原配置 10 分钟结果，因此不计算本轮的完整加速或 CPU 节省比例。
- 手机取消后，PC 继续识别并正常结束。临时进程已清理。正式 Voice 和 VPlus 未重启。

## 方法

在同一台 RTX 4090 上，依次测试默认等待和被动等待。两组计划时长均为每路 600 秒。每组使用独立进程、临时 systemd unit 和本机端口 `18098`。模型加载及预热结束后才开始计量。

两路通过真实 PC / 手机 V1 协议同时送入受控中英文音频。输入按实际采集速度发送，每 24 秒同时执行一次句段收尾。保持同一模型、音频、起点、角色、FP16、两路容量、1 GiB KV 缓存、160 ms 步长和 16 秒窗口。CPU 特征路径保持不变，worker 仍用 4 线程。默认组未设置 `OMP_WAIT_POLICY`，没有强制设置为 `ACTIVE`。

正式服务空闲且模型驻留。测试同时监控正式桌面录音及 API 会话。若正式听写恢复，隔离测试会停止。未操作用户输入框、tmux、VPlus 或共享权重。

## 结果

| 项目 | 原配置，本轮未完成 | 被动等待，完整 600 秒 |
| --- | ---: | ---: |
| 每路实际产生音频 | 202.4 秒 | 600 秒 |
| CPU 计量窗口 | 203.709 秒 | 601.492 秒 |
| 服务 CPU 核秒 / 平均逻辑核数 | 530.992 / 2.607 | 630.191 / 1.048 |
| 普通音频步骤 p95：PC / 手机 | 197.779 / 198.140 ms，部分记录 | 128.017 / 129.361 ms |
| 音频积压 p95：PC / 手机 | 1.4872 / 1.4895 秒，部分记录 | 0.2728 / 0.2750 秒 |
| 后段相对前段积压 p95 的变化 | 无完整长测结果 | -0.0025 / -0.0021 秒 |
| 最后收尾耗时：PC / 手机 | 未到正常收尾 | 0.2314 / 0.2156 秒 |
| 长测验收 | 失败 | 通过 |

p95 表示 95% 的观测值不超过此数。音频积压表示已采集音频尚未被模型处理完的时间差，不是文字显示到输入框的总延迟。普通步骤时间也不等于首次出字时间。

两列的有效时长不同。原配置的部分数值只用于排查，不能与候选完整结果组成同条件性能比较。完整的 120 秒对照及其 CPU 节省比例仍见前轮报告。

被动等待的每路 9,600,000 个样本全部发送、接收并处理；3,750 个音频事件、24 个句段收尾事件和 1 个最终收尾事件全部齐全。没有固定文字前缀倒退、流控错误或串流。每分钟均有积压记录，后段增长通过预先设定的 `≤0.1 秒` 门槛。模型代次与 worker 保持。

本轮原配置没有最终全文，不能用于全文比较。另与此前完整 600 秒记录 `baseline2-repeat` 核对：同一模型、音频 hash、角色、起点、时长、帧长、收尾规则和引擎配置匹配，两路最终转写 hash 均相同。这个历史记录只用于文字核对，不用于本轮速度或 CPU 比较。文字一致的结论只覆盖这两份受控循环音频。

## CPU 与 GPU

CPU 总量来自独立服务 cgroup 的起止差，包含所有子进程和调用间等待，排除模型加载、预热、客户端及监控工具。平均逻辑核数使用实测计量窗口计算。一个逻辑核表示每秒消耗一个 CPU 秒，不区分 P / E 核的算力。

另每约 30 秒取样，观察 CPU 是否持续增长。被动等待的有效区间约为 1.00–1.11 核，前、后段约为 1.043 / 1.054 核，没有观察到持续上升。这里描述实测趋势，没有临时设定新的 CPU 稳定性门槛。

区间观察覆盖候选计量窗口的 94.97%；开始约 1.20 秒和末尾约 29.08 秒没有独立完整区间。最后一段跨过性能窗口，已从趋势统计中排除。原配置观察器启动较晚，覆盖 59.06%，前约 72.64 秒和后约 10.76 秒没有区间记录。这些缺口不影响 cgroup 起止差的总量，但不能声称全程都有 30 秒区间证据。

候选的 API、worker、EngineCore 分别消耗约 36.80、194.05、399.37 个 CPU 秒。这是总量的辅助分解，不能再加到 cgroup 总量上，也不能把全部 CPU 消耗当作音频预处理。

候选的整卡 GPU 活动率均值为 27.77%，峰值为 52%；实验进程显存峰值之和为 6414 MiB。整卡数据包含桌面及正式驻留模型，进程峰值也不保证同时发生。不能据此按比例推算最大并发数。本轮没有测试 GPU 特征组合或新增并发。

## 失败、取消与收尾

原配置触发 `CAPTURE_BUFFER_EXCEEDED`。每路已产生 3,238,400 个样本，发送 / 接收 3,207,680 个，处理 3,176,960 个；仅有 1,241 个音频处理事件和 8 个句段收尾事件，没有最终收尾。报告保留 `passed=false`、`measurement_valid=false`。这是一次实际失败，没有重跑挑选结果。

该次整卡显存峰值为 15481 MiB，没有 GPU OOM 证据。第 4 分钟的部分记录显示积压 p95 已升至约 3.78 秒。现有记录支持“音频积压触发保护”，尚不能确定唯一根因，也不能把这次失败解释成原配置每次都会失败。

候选长测后另做 24 秒取消检查。手机第 8 秒取消，收到明确 `final(reason="cancelled", complete=false)`；PC 继续完成 384,000 个样本并收到正常结束。模型和 worker 保持，两路状态独立。

两组临时 unit 均已退出，无残留实验 PID 或会话。结束时正式 Voice 为 `ready / qwen-stream / cuda:0`，容量 2，无活动会话；桌面为 `idle`。Voice API PID 313597、worker PID 3268033、EngineCore PID 3269836 保持。VPlus PID 7301、启动时间 `2026-09-30 23:20:01 CST` 保持，健康接口为 200。本轮结果只适用于 R2T2；当前正式 Qwen 模式没有做同样长测。

本轮未修改推理代码，没有重跑前轮已通过的 264 项 CPU 单元 / 组件测试。新增证据来自真实 GPU 和本机双协议流测试，不替代 Android 真机、跨网、桌面粘贴或 VPlus 同时满负载验收。

## 证据与复现

[JSON 证据](evidence/cpuwait-longrun-2026-10-03.json) 保留原配置失败与候选独立验收。总 `passed=false` 表示完整对照未成立；`candidate_longrun_acceptance.passed=true` 表示候选自身通过，二者含义不同。原报告、观察器、汇总脚本和输入 manifest 的 hash 均已记录。未提交音频、凭据或完整转写。

准备独立 runtime、凭据和 `pair-ab` manifest 后，使用新的 label 复现候选：

```bash
.venv/bin/python tests/run_capacity_profile.py \
  --live-runtime "$HOME/tools/oneaxe-voice/runtime" \
  --label new-passive-longrun --capacity 2 --kv-gib 1 \
  --omp-wait-policy passive --feature-device cpu --check-cancel \
  pair-ab:600
```

原始证据位于忽略目录 `work/capacity/cpuwait-long-*-20261003*`。区间观察器和汇总脚本位于 `work/longrun-study/`。汇总脚本因完整对照不成立返回退出码 1，候选自身的验收结果单独保留。
