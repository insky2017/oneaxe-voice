# 验证记录

日期：2026-10-03。Qwen 统一接口已部署，完成本机 F9 / GTK 端到端和 e15l 安装版真实双路验证。Android 真机与 e15l 解锁后的桌面 F9 不在本轮验收范围。

## 统一模型契约源码改动

当前 Linux 源码已移除 `mode == r2t2` 的启动白名单，兼容服务端通过同一移动 V1 发布的 R2T2 与 Qwen 流式能力。协议、音频、流控、就绪状态、模型代次和名额仍需验证；远端 `start` 不发送 `model`、`model_id` 或 `mode`。`MODEL_UNSUPPORTED` 提示表示服务端尚未接入移动 V1 协议，不表示模型本身没有流式能力。

服务端 `6676e23` 已部署，两机新版客户端已安装并重启。Qwen 新证据见 [统一接口正式验收](evidence/unified-stream-production-2026-10-03.json)：本机 10 秒安装版识别通过；PC 与 e15l 600 秒双路通过，观测重叠 599.7707 秒，PC / 远端分别处理 9920000 / 9600000 样本，全部等于发送量，关键语检查未检出串路。PC 处理进度 P95 为 2.096 秒，末段相对前段变化 -0.0188 秒；远端未发送缓冲峰值 5120 样本，已发送未处理峰值 34560 样本。

本机真实 F9 → Pulse 测试音源 → HTTPS/WSS / Qwen → GTK 输入框的 53.403 秒完整流程通过：停顿出字、F9 停止补尾、焦点变化只复制、回到旧窗口不补贴、取消无迟到输入、不附带回车。实际复制按钮取得的全文与目标输入框 48 字逐字一致；临时音源、设置、焦点及剪贴板均已恢复。这是受控音源和 GTK 目标的证据，不替代任意应用故障场景或 Android 真机验收。下方保留此前 R2T2 历史验收，不混用两轮哈希和数据。

本次本地 `cargo test --locked` 通过 59 项库测试与 10 项 GUI 状态/交付测试；覆盖按能力接受 Qwen/其他模型标识、拒绝不一致能力、远端 start 字段不变，以及 Qwen 能力下的有序 flush/finish 和取消后的迟到文字阻断。`cargo fmt --all -- --check`、两套 Python 脚本语法/CLI 检查和 `git diff --check` 通过。默认 `cargo clippy --all-targets --locked` 通过，保留既有桌面/界面告警；严格 `-D warnings` 被原有 `src/desktop.rs:275` 的 `comparison_to_empty` 和 `:561` 的测试类型复杂度告警阻挡，默认检查另报告 `src/ui.rs:426` 的 `manual_c_str_literals`。

兼容 release 已在 e15l 的 Ubuntu 20.04 / glibc 2.31、Rust 1.89.0 环境离线构建，复用隔离 `runtime/cargo` 与现有 target 缓存。冻结远端文件为 `runtime/unified-v1-build-20261003/oneaxe-voice-linux`，本机取回文件为 `runtime/oneaxe-voice-linux-unified-v1-ubuntu20.04`；两端 SHA-256 均为 `67fdeb2fd7b7ff222521d501f12cfc59e241d91e0953a148b0958db4bf1047fc`。e15l `ldd` 没有缺失库，所需最高 glibc 符号为 `GLIBC_2.29`，两端 `--version` 均正常。主控随后将该文件安装到两机 `~/.local/bin/oneaxe-voice-linux` 并重启空闲托盘进程，复核安装文件哈希一致。

## 真实桌面与双路

已通过 45 秒真实隔离测试：e15l 测试进程断开约 0.203 秒后释放名额；原 PC 会话保持不变，断开后继续增加 55 次固定文字并正常 finish。额外 Linux 客户端被容量限制拒绝且没有启动采音。此项证明断线隔离，显式 cancel 另由桌面流程与协议测试覆盖。

本机完整 F9 桌面流程已通过（`runtime/local-gui-final-retry.json`，52.812 秒）：经实际 Pulse 输入源、WSS/R2T2、真实 GTK 输入框，停顿时出字、F9 停止补尾；最终输入框与点击真实“复制”按钮取得的全文均为 44 字且逐字一致。切到另一窗口后只复制，切回仍不自动补贴；取消后没有迟到输入，没有自动回车，临时配置/音频源/剪贴板/焦点均已清理恢复。此项是 GTK 目标证据，不能代替 Codex 输入框的故障修复验证。

本机先前 GNOME 锁屏导致测试受阻，现已在用户解锁后复验。夹具增加锁屏前置检查，并允许窗口映射期间暂时查不到活动窗口，仍要求焦点连续三次稳定才开始测试。没有放宽产品的目标或焦点核验。用于读取“复制”按钮的用户级辅助功能总线曾有失效 socket，已重建后验证；未重启 Voice、VPlus 或修改服务源码。

用户已明确接受 e15l 按远程条件做有限测试；不再把解锁后的 F9 / 自动输入验收列为本次远端交付必需项。远端证据只包括安装、鉴权、采集、真实识别、双路连接与断线隔离。

正式 10 分钟双路复验已通过（`runtime/dual-stream-final-600.json`）。PC 发送 620 秒中文音频；e15l 安装版客户端发送 600 秒英文音频。采样观察到同时活动 599.9398 秒（采样间隔 0.5 秒）；两端关键语匹配、未发现另一声道关键语，模型代次与 worker 保持。PC 全部处理 9920000 样本，末期相对初期处理延迟 P95 变化为 -0.0049 秒；远端全部处理 9600000 样本，首次固定文字 1.850 秒，最大观察积压 0.64 秒，未发送队列最大为 0。样本首字时间不代表一般口述延迟保证，远端没有独立的早晚期延迟分布指标。

历史失败报告保留：先前中断的一轮未生成报告；另一次实际重叠 600.0621 秒、远端客户端退出 0，但 SSH 封装的缓冲 stdin 守护线程在 Python 退出时触发 fatal error。已将 lease 改为 `select + os.read` 并在退出时回收线程；真实短测和上述正式长测均通过。旧失败报告没有改为成功，也没有补造已丢失的指标。

早期尝试不计为通过：测试目标程序在 GTK3/GTK4 同存时需明确指定 Gdk3；`xdotool search` 默认 `--any` 曾误把 A 窗口当 B，已修为 `--all` 并复核 PID/窗口 ID。e15l 首次 F9 测试被锁屏阻止。新生成英文样本未识别出预定关键词，首轮约 600 秒双会话测试因此没有通过，已改用此前验收过、短测也通过的受控样本。以上问题与后续正式结果分别保留。

## 复验入口与证据范围

- `tests/gui_e2e.py`：真实 F9、专用 Pulse 测试输入、GTK 测试输入框；恢复配置、剪贴板、焦点并删除临时转写。
- `tests/dual_stream.py`：PC 620 秒、e15l Rust 客户端 600 秒；复用现有服务测试 helper，不修改服务文件；记录实际双会话重叠。
- `tests/remote_isolation.py`：PC 持续时检查额外远端容量拒绝、终止 e15l 测试进程后的会话隔离。进程终止/断线不等同于显式 cancel。
- 两个脚本均从服务状态读取当前 PC 模式并在整轮验证模型代次和 worker；可用 `--expected-mode qwen-stream` 或 `--expected-mode r2t2` 断言测试对象，不切换模型。远端由安装版 Rust 客户端按 capabilities 判断是否可开始，不用 PC 管理凭据查询移动接口。
- 双路脚本的 PC 处理延迟阈值用 `--max-processed-lag-seconds` 配置，默认仍为 2 秒；Qwen 2 秒块式推理复验显式传 `2.5`。延迟增长阈值为 0.5 秒，固定文字间隔为 30 秒。远端已发送但未处理的样本积压用 `--max-observed-lag-samples` 配置，默认 `32000`，Qwen 复验显式传服务端流控额度 `34560`；客户端未发送缓存仍不得超过 `32000` 样本。报告分别保存两类阈值。
- 原始报告存于 Git 忽略的 `runtime/`；只保存状态、指标、校验结果与哈希，不保存凭据或转写正文。
- 可随代码审阅的精简证据见 [验收数据](evidence/acceptance-2026-10-03.json)。[重复输入调查](duplicate-input-investigation.md) 明确列出目标延迟读取的已复现风险及尚未完成的修复。

物理麦克风测试、受控音频识别、桌面自动输入、协议逻辑测试分别证明不同环节。此前首版已验收 GNOME X11、Tailnet、R2T2、1 PC + 1 远端；此次 Qwen 统一 V1 改动待真实复验。公网、Wayland 自动输入和多远端未实现。
