# Qwen 流式：CPU 被动等待优化

日期：2026-10-03。代码提交 `2c5f427` 已部署到正式 `master`。Qwen 流式已就绪，可继续使用。R2T2 此前已启用相同策略。

## 要点

- Qwen 流式现在也使用 `OMP_WAIT_POLICY=PASSIVE`。CPU 线程在等待时休息，减少等待消耗。
- 同样的 2 分钟输入，服务 CPU 平均占用从 **0.255 核降到 0.152 核**，减少约 **40%**。绝对减少约 0.10 个逻辑核。
- 每一步的固定文字、候选文字和最终全文均一致。首次固定文字出现时间基本不变。
- 正式部署后，再次完成连续识别、取消和重新录音检查。204 项 CPU 单元 / 组件回归通过。

## 改了什么

[Worker 启动代码](../oneaxe_voice/engines.py)现在为 Qwen 流式和 R2T2 两种子进程设置被动等待。仍使用 4 个 CPU 线程。父服务环境不变，没有调整 systemd 全局环境或 VPlus。

CPU 继续做音频特征处理，GPU 继续做模型推理。本轮没有启用 GPU 特征处理，没有改识别算法、模型权重、标点、稳定前缀规则或音频窗口。Qwen 仍为单路流式；本轮没有开放 Qwen 手机并发。

已安装的官方实现为 qwen-asr 0.0.6、vLLM 0.14.0、transformers 4.57.6、torch 2.9.1。Qwen 的调用链未覆盖 Whisper 特征提取器默认的 CPU 设备。此项是源码核对，没有新增特征设备探针。

## 隔离对照

原配置和候选各运行一次 120 秒。它们使用相同受控中文样本、160 ms 输入帧，并在第 40、80 秒执行 `flush`。每段连续音频超过 30 秒，覆盖 Qwen 的窗口轮换。每组均完成 750 个音频回复、2 个停顿收尾回复和 1 个最终回复，1,920,000 个样本全部发送并确认。

测试从源码决定子进程策略：原配置为 `08899f4` 的 Qwen 启动代码，候选为 `2c5f427`。两组 API 父进程均清空 OMP / GOMP / MKL / KMP 等相关覆盖项；实际 worker 分别为默认等待 / PASSIVE，线程数均为 4。模型加载和预热不计入测量窗口。正式服务保持空闲和模型驻留。

| 指标 | 原配置 | 被动等待 |
| --- | ---: | ---: |
| 服务 CPU 平均逻辑核数 | 0.2554 | 0.1522 |
| 每 2 秒触发的推理耗时 p95 | 263.18 ms | 225.31 ms |
| 160 ms 音频帧回复延迟 p95 | 130.11 ms | 115.27 ms |
| 首次固定文字 | 8.148 秒 | 8.124 秒 |
| 最后收尾 | 0.121 秒 | 0.090 秒 |

CPU 数字来自独立服务 cgroup 的起止差，包含 API、worker、EngineCore 等子进程，排除测试客户端和监控程序。不是音频预处理本身的占用。一个逻辑核表示每秒消耗一个 CPU 秒，不等于整机占用 100%。

Qwen 每 2 秒才触发一次主要识别，大部分 160 ms 请求只是接收音频。因此，表中分别列出主要推理与所有音频回复的延迟。首次出字还取决于样本内容和稳定前缀规则；此次主要收益是减少 CPU 消耗，不应期待首次出字提前数秒。

比较门槛在测前记录：CPU 至少下降 20%；主要推理 p95 和收尾允许 20% 或至少 100 ms 的波动；音频回复 p95 和后段增长不超过 100 ms；输入、逐事件文字 hash 链和最终文字 hash 一致。全部通过。候选后段回复延迟 p95 相对前段变化为 -7.34 ms。

这些结果来自每组一次受控 2 分钟测试，不是所有音频的平均收益，也不是新增 10 分钟长测。没有把 R2T2 的测试结果算作 Qwen 证据。

## 正式部署与回归

确认桌面和 API 空闲后，将代码快进到正式目录，只重启一次 `oneaxe-voice.service`，重新加载 Qwen 流式。运行进程的工作目录及源码 hash 与已通过的候选一致。实际 worker 环境为 `PASSIVE / 4`，模型在 `cuda:0` 上就绪。

正式接口再次完成相同的 120 秒输入，全部样本发送并确认，收尾完整。逐事件固定 / 候选文字 hash 和最终全文 hash 与隔离候选一致。服务 CPU 平均占用 **0.1605 核**；主要推理 p95 为 227.78 ms，音频回复 p95 为 117.94 ms，最终收尾为 0.096 秒。

之后第 8 秒取消一次，再完成一轮 12 秒识别。Qwen 使用旧 WebSocket 协议，取消时正常关闭连接，没有 R2T2 V1 的取消 `final`；取消可以主动丢弃尚未发送的尾部音频。新一轮正常结束，worker 和模型代次保持。正常测试没有音频丢失，取消场景不按“全部音频处理完”验收。

最终 Qwen 保持 `ready / cuda:0`，无活动会话。桌面、托盘和 VPlus 未重启；三份桌面 / 模型策略 / 移动监听配置的 hash 保持。VPlus PID 7301、原启动时间保持，健康接口为 200。两组隔离服务均已清理，无残留进程。

EngineCore 会改写进程名，导致 `/proc/environ` 原始区域不可直接读取。本轮实际确认的是 worker 的等待环境，不将子引擎继承机制写成直接观测结果。

CPU 测试命令如下，204 项通过，包含两种流式 worker 的策略设置、父环境隔离、30 秒窗口和尾部收尾检查：

```bash
OMP_NUM_THREADS=1 CUDA_VISIBLE_DEVICES='' \
  .venv/bin/python -m unittest discover -s tests -q
```

本轮真实模型验收走 Qwen 接口，没有重放桌面粘贴、tmux、Android 麦克风或跨网测试，也没有测 VPlus 同时满负载。

## 证据与复现

[JSON 证据](evidence/qwen-passive-release-2026-10-03.json)包含两组对照、正式回归、来源 hash 和部署来源。原始数值报告位于忽略目录 `work/qwen-passive-release/`；证据不包含音频、完整转写或凭据。

新增[协议客户端](../tests/e2e_qwen_wait.py)、[隔离 runner](../tests/run_qwen_wait_profile.py)和[进程隔离辅助代码](../tests/wait_profile_support.py)。CPU 模拟检查覆盖协议正常结束、确定性 hash、取消、前缀回退、队列溢出和超时；它们与真实 GPU 结果分别记录。

使用独立 checkout、新的 label 和已授权的至少 10 秒、16 kHz 单声道 PCM16 WAV，可复现候选：

```bash
.venv/bin/python -m tests.run_qwen_wait_profile \
  --label new-qwen-passive --policy passive \
  --audio /path/to/test.wav \
  --live-runtime "$HOME/tools/oneaxe-voice/runtime" --check-cancel
```

runner 只读取正式录音状态，测试服务使用独立本机端口 `18099`。正式听写恢复时，会中止并清理实验。`--policy` 用于核对源码实际启用的策略，不是强制覆盖开关；原配置基线需要使用优化前的 Worker 启动代码及相同测试脚本。不要在正式目录回退代码来做基线。

若需撤销此次 Qwen 策略，在所有听写会话空闲时执行 `git revert 2c5f427`，重启 Voice API 并重新加载所选模式。它会恢复 Qwen 原等待方式，保留此前 R2T2 的 PASSIVE 设置。本轮未执行回滚。
